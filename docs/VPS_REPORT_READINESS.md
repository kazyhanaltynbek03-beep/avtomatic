# Подготовка VPS: готовые отчёты при открытии страниц

На VPS приложение должно постоянно работать, а серверные страницы должны читать сохранённые данные. Синхронизация маркетплейсов и пересчёт снимков выполняются фоновыми процессами.

## Что подготовлено в проекте

- `compose.yaml` запускает PostgreSQL с постоянным томом, миграцию и bootstrap Owner, отдельную очередь задач, веб-приложение и отдельный worker отчётов.
- До запуска веба `report-cache-warmup` создаёт снимки для сегодня, вчера, текущей и прошлой недели, текущего и прошлого месяца, квартала, полугодия, года, прошлого года и последних 370 дней.
- Для каждого диапазона фоновый worker сохраняет краткую сводку и полный отчётный снимок из того же финансового движка. Полный прогрев включён в `compose.yaml` для VPS. `/api/report` для Overview/Analytics читает готовый снимок, если он уже есть.
- Пользовательский диапазон, которого ещё нет в базе снимков, рассчитывается один раз и сохраняется. При повторном открытии этот период читается из базы.
- После открытия сайта worker обновляет стандартные снимки отдельно от HTTP-запросов. Формулы выручки, возвратов, себестоимости и прибыли не переписываются.
- Пул соединений PostgreSQL по умолчанию ограничен пятью соединениями на процесс с пятью дополнительными. Uvicorn остаётся в одном worker-процессе, чтобы не запускать несколько копий фоновых циклов.

## Первый запуск на VPS

1. Установить Docker Engine и Docker Compose v2, затем скопировать проект на VPS.
2. Создать `.env` из `.env.example`. Задать уникальные длинные `POSTGRES_PASSWORD` и `OWNER_PASSWORD`, `CREDENTIAL_ENCRYPTION_KEY`, `COOKIE_SECURE=true`, а также реальные API-настройки.
3. Настроить HTTPS reverse proxy перед `127.0.0.1:8000`.
4. Запустить `docker compose up --build -d` и дождаться `report-cache-warmup` и healthcheck сервиса `web`.
5. Проверить `/api/health`, затем войти под Owner и подключить маркетплейсы. Синхронизация данных идёт отдельно; отчёты показывают сохранённый снимок, пока worker обновляет его после поступления новых данных.

Для восстановления уже заполненной базы сначала восстановить PostgreSQL и каталог `/srv/uploads`, затем выполнить миграции, прогрев и запуск compose. Не включать demo-режим на базе с рабочими данными.

## Ограничение первого произвольного диапазона

Нельзя заранее вычислить каждый возможный пользовательский диапазон дат. Первое открытие нестандартного диапазона, которого ещё нет в кэше, всё ещё требует вычисления; после этого результат сохраняется и повторно открывается быстро. Стандартные кнопки периода прогреваются до запуска веба. Если при первом переносе требуется нулевая задержка именно на любом произвольном диапазоне, нужно заранее загрузить этот диапазон и дождаться его снимка.

## Проверка состояния

```bash
docker compose ps
docker compose logs --tail=100 report-cache-warmup report-cache-worker web
curl --fail http://127.0.0.1:8000/api/health
```

Для резервного копирования использовать штатный `pg_dump`/`pg_restore` и копию постоянного тома uploads. `.env` и ключи интеграций хранить отдельно от git и резервных архивов с исходниками.
