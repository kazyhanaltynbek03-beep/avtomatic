# Архитектура и финансовые правила

## Развёртывание

Один модульный FastAPI backend обслуживает REST API и собранный React frontend. React/Vite выбран вместо Next.js: внутреннему ERP не нужны SSR/SEO; один origin упрощает защищённые cookie и CSRF. PostgreSQL 16 — основная БД. SQLAlchemy + Alembic. Отдельный процесс worker читает устойчивую очередь PostgreSQL с SKIP LOCKED. Данные и задания не хранятся в памяти браузера.

Это одно рабочее пространство одного владельца с несколькими ИП/ТОО, а не многопользовательский SaaS с изоляцией между независимыми арендаторами. Для другого независимого клиента разворачивается отдельный экземпляр. Один физический склад; каждая партия имеет юридического владельца. Продажа может списывать партии только своей компании. Межфирменная передача остатков не реализована: её нельзя подменять скрытым расходованием чужого товара.

## Схема

- companies → accounts, customers, purchases, batches, sales, returns, expenses, cash, documents.
- products → batches, sales, movements.
- purchases → batches (1:N); стоимость закупки включает распределённые дополнительные затраты.
- sales → allocations → batches: сохранённый исходный FIFO, включая количество и стоимость возвратов.
- returns → sales: обратные операции; восстанавливают исходные партии и первоначальную себестоимость.
- movements: неизменяемый складской журнал, подписанные количество и стоимость.
- cash: отдельные денежные операции; связь с продажей, закупкой или расходом (максимум одна).
- users → sessions; users.role + users.company_ids определяют права.
- audit: запись важных действий, без паролей и токенов.
- jobs: queued → running → done / failed; аренда задания 15 минут, ручной повтор максимум 3 попытки.
- imports: исходные строки, mapping, fingerprint, ошибки, подтверждение.
- niches: наблюдения, источник, дата, описанная эвристика.
- settings: название, KZT, Asia/Almaty.

Полная воспроизводимая схема — `backend/migrations/versions/*initial_schema.py`. ORM — `backend/app/models.py`. OpenAPI — `/api/openapi.json`, Swagger — `/api/docs`.

## Денежные единицы и расчёты

В REST API суммы — целые тиыны, кроме `/calculator` (десятичные тенге). UI, импорт и экспорт отображают/принимают тенге. Никаких float для сумм проводок. FIFO делит остаточную стоимость партии пропорционально количеству с ROUND_HALF_UP; последняя единица получает остаток. Суммарная стоимость сохраняется точно. Дополнительные затраты закупки распределяются пропорционально закупочной стоимости; остаток округления получает последняя строка.

Revenue = продажи − возвраты по дате соответствующего события.
COGS = стоимость списанных партий − стоимость возвращённых единиц.
Gross Profit = Revenue − COGS.
Net Profit = Gross Profit − комиссии − логистика − реклама − зарегистрированные расходы.
Маржа = Net Profit / Revenue × 100.
ROI = Net Profit / (COGS + комиссии + логистика + реклама + расходы) × 100; при нулевой базе null.
Cash Flow = сумма денежных операций за период.
Cash = сумма денежных операций по конец периода; начальное сальдо вводится отдельным платежом.
Стоимость склада = сумма стоимости складских движений по конец периода.
Дебиторка = max(продажа − возвраты − платежи по продаже, 0).
Обязательство возврата = max(полученные деньги − выручка после возвратов, 0).

Покупка не является расходом периода. Оплата закупки влияет на деньги. Списание повреждённого товара признаёт расход по FIFO. Ввод начальных остатков не создаёт прибыль. Возвращённый товар считается пригодным к продаже; повреждённый товар после возврата списывается отдельной корректировкой.

Комиссии, логистика и реклама в продаже — начисленные затраты. Их оплата регистрируется отдельно в Cash Flow; не создавайте второй расход для уже включённой комиссии. Если маркетплейс перечислил деньги за вычетом комиссии, для полного закрытия дебиторки зарегистрируйте валовое поступление и отдельное денежное списание комиссии. Автоматической сверки нет.

Налоги, НДС, курсовые разницы, амортизация и регламентированная бухгалтерия не рассчитываются автоматически. Налоги/прочие расходы учитываются после ручной регистрации. Раздел «Бухгалтерия» — управленческие регистры и выгрузки, не замена 1С и официальной отчётности.

## Транзакции и ограничения

Операции атомарны; PostgreSQL блокирует компанию и товары, затем партии. Нельзя продать больше остатка, вернуть больше проданного, получить оплату сверх задолженности или выдать возврат сверх полученного. Денежные/складские документы не редактируются и не удаляются. SKU и справочники имеют CRUD; использованные FK запрещают удаление. Номера документов уникальны в рабочем пространстве; для внешних отчётов добавляйте префикс канала/аккаунта к номеру.

Складские операции выполняются хронологически: нельзя провести операцию раньше последнего движения компании. Это защищает исторический FIFO. Заднее число требует отдельной процедуры перепроведения, которой в этой версии нет. Для прошлых данных импортируйте по возрастанию дат. Продажи одной строкой — один SKU; несколько SKU можно провести несколькими строками с разными reference. Резервирование, сборка комплектов и учёт серий не реализованы.

Отчёты работают по датам операций (учёт начислений); Cash Flow отдельно по датам оплаты. Общие расходы без account_id остаются на уровне компании и не распределяются по каналам автоматически. Для канала отображается прибыль после отнесённых на него затрат, а не после произвольного распределения общих расходов.

## Безопасность

Argon2 хеширование. Случайная 384-битная opaque session; в БД только SHA-256 токена; срок 12 часов. HttpOnly, SameSite=Strict, Secure включается в production; mutating API требует X-CSRF-Token. Смена пароля отзывает все сессии. Роль и активность читаются на каждый запрос. Лимит входа: 8 попыток / 15 минут на identity; в production добавьте rate limiting на reverse proxy.

Owner видит всё. Остальные роли ограничены company_ids. Права проверяются сервером, а не только меню. AI tool читает авторизованный отчёт, не выполняет SQL из запроса и не имеет инструментов изменения данных. Ключи провайдеров в environment; в БД аккаунта только имя переменной. Файлы вне public root, скачивание через проверку сессии и компании. Ограничены размер и тип; CSV/XLSX export защищён от formula injection. Для антивирусной проверки загружаемых документов нужен отдельный сканер.

## AI и внешние системы

Assistant использует OpenAI Responses API + get_business_snapshot. Расчёты детерминированы, текст AI — интерпретация, поэтому интерфейс отдельно показывает исходные цифры. Карточки передают данные поставщика и опционально фото; результат — черновик для проверки. Designer вызывает Images API и сохраняет результат приватным документом. Без ключа задача явно завершается ошибкой, а не выдаёт сгенерированную заглушку.

KaspiConnector / WildberriesConnector / OzonConnector — интерфейсы, явно отклоняющие live sync до реализации и проверки API контракта. Ключ сам по себе НЕ активирует готовый live adapter. DemoAdapter проверяет очередь и UI, не пишет продажи. CSVAdapter направляет к нормальному импорту. Для живого адаптера реализуйте fetch() с курсором, постраничностью, rate limiting и нормализацией; сначала stage/import preview, затем те же финансовые сервисы. Не пишите напрямую в sales/batches.

Niche Analyst не скрейпит чужие сайты: принимает реальные наблюдения и ссылку/название источника. Без минимального набора данных score отсутствует. Формула видна в ответе; источник помечается как предоставленный пользователем, без утверждения о независимой проверке. Forecast использует средние дневные значения, не LLM и не обещание будущего результата.

## Эксплуатация

PostgreSQL + uploads volume необходимо резервировать вместе. Пример БД: `docker compose exec -T db pg_dump -U qor qor > backup.sql`. Файлы uploads включайте в защищённую резервную копию с соответствующим сроком хранения. Перед обновлением: backup → migration staging → tests → deployment. Не оставляйте demo-данные, demo-password и COOKIE_SECURE=false на публичном сервере. Один worker допустим локально с SQLite; PostgreSQL нужен для нескольких web workers и очереди в production.
